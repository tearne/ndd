# Python installer for deployment

**Mode:** Formal

## Intent

NDD currently installs via `curl … | bash` running `install.sh`, which fetches the method from GitHub raw `main` into `ndd/` (see *Distribution*). Switch the deployment method to a Python opt-in installer, in the style of the earlier `opt-in.py`: a readable script the user runs deliberately and can inspect first, rather than piping a remote shell script straight into `bash`. The preference is trust and legibility — the installer can be read before it runs and reports what it touches.

The *Distribution* behaviours must survive the switch: vendoring the method into `ndd/`, wiring the entry files, gitignoring, and idempotent re-run/upgrade (including the `ndd.prev.md` backup).

Lands before the go-live reorg (130), which then proves the chosen installer end-to-end against the live repo.

Beyond the switch, make this repo consume the method the way a client does: vendor a snapshot into `ndd/` with `opt-in.py` and orient off it. The vendored copy lagging the root source is deliberate — a promotion-to-trial gate, so the agent never runs off a half-finished map — which dissolves the long-standing special case of a bespoke development entry diverging from the shipped `BOOTSTRAP.md`.

## Approach

### Local-clone copy model, like the original opt-in.py

The consumer clones the NDD repo wherever they like and runs it from their project (`path/to/ndd/opt-in.py`). The script copies the method out of its own checkout — its source of truth is its own directory, as the original `opt-in.py`'s was — rather than fetching over the network. Upgrading is `git pull` in the clone, then re-run. This drops `NDD_BASE_URL` and the remote fetch entirely.

### Keep install.sh's ndd/ vendoring layout, only change the source

Reproduce `install.sh`'s outcomes into the consumer's cwd from the local checkout: vendoring into `ndd/` (map as `ndd.md`, `BOOTSTRAP.md`, `CHANGELOG.md`, `standards/`), the `ndd.prev.md` backup on change, entry-file pointers written only when absent or already matching (warn otherwise), and gitignore wiring. Substance of *Distribution* is unchanged; only the transport becomes a local copy. Not the original `opt-in.py`'s `changes/agent/<version>/` layout.

Copying from a local checkout, the whole `standards/` directory is copied wholesale rather than enumerating each guide by name as `install.sh` does — so adding a guide needs no installer edit. The current `standards/` contents are exactly the ship list, so nothing is excluded.

### POS-compliant single script, uv required

Follow the *POS* standard: one file, a `uv` script shebang with a PEP-723 header, `rich` output, `--version`. `uv` is a stated prerequisite. Deviate from POS's hardcoded version constant by reading the top `CHANGELOG.md` heading instead — since the installer runs from the checkout, the changelog is the single source of truth and there is nothing to bump twice.

### Dogfood by self-vendoring; staleness is the gate

This repo consumes the method as a client does: `opt-in.py` vendors a snapshot into `ndd/` and the repo orients off it. The vendored copy lagging root source is the point — re-running the installer is the conscious promotion-to-trial. The self-install guard is narrowed to allow this (it refuses only if the target `ndd/` *is* the source directory).

### A universal read-only rule on ndd/ dissolves the dev entry

`ndd/` is a vendored snapshot regenerated by `opt-in.py`, so it is read-only for every consumer — hand-edits there vanish on the next install. Shipping that rule in `BOOTSTRAP.md` pushes all edits out of `ndd/`: for a consumer, into their own project; for this repo, into the root `map.md`/`BOOTSTRAP.md`/`standards/`, which *are* the source (this project's map and the method's map are the same file). No dev-specific knowledge is needed, so the dev `CLAUDE.md` can be a pure `@ndd/BOOTSTRAP.md` pointer, byte-identical to a consumer's — the special case fully dissolves. Phrase it as "regenerated, never hand-edit", not "editable when updating ndd", so no agent thinks it may edit `ndd/` in place.

Because the dev entry is now pure boilerplate, it is gitignored and regenerated like a consumer's — `opt-in.py`'s existing entry/gitignore wiring is already correct, so no `--vendor-only` flag is needed.

### Retire install.sh; update BOOTSTRAP and the repo README

Delete `install.sh`. Repoint `BOOTSTRAP.md`'s "Staying up to date" to the new flow (`git pull` the clone, re-run `opt-in.py`), and give the repo `README.md` an installation section stating the `uv` prerequisite and the clone-and-run steps. The *Distribution* map node is caught up per-node afterwards.

## Unresolved

All resolved — the universal read-only rule removes the need for both a bespoke dev entry and a `--vendor-only` flag; converting now, as agreed.
